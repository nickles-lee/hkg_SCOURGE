# V23 integration and release gates

## Scope and status

V23 is a new, separate standalone release candidate on
`wireless-carplay-confirmed-fixes`, not a replacement of an existing V20/V21/V22
bundle. It combines the reviewed CarPlay safety checkpoints, latest upstream
work, and the V22 BlueLink-safe / Orange Pi USB-SSH work using merges, not a
rebase. Existing source branches are not rewritten.

**Offline integration candidate; no end-to-end iPhone or car validation.** An
independent source review, synthetic helper exchange, or namespace network test
does not establish real MFi authentication or working wireless CarPlay.

## Preserved boundaries

- GB, phone-first/home-network-second configuration, owner credentials and all
  three owner SSH keys; no key bytes or personal network details in Git.
- Modem defaults and vendor routes, wired USB projection, shared micom behavior,
  Battery/charge-door/cluster, Tweaks and Reboot.
- Two install files: `run_stuff.sh` and `appcombo.tar.gz`; no WiFi reinstall,
  migration stage, or manual WiFi-Off prerequisite.
- Unknown files, keys, route records, overrides and backups are not silently
  adopted or deleted. A legacy format alone is not ownership evidence.
- No automatic activation of experimental wireless transport/auth/receiver
  components. In particular, helper bytes are not phone authentication success,
  and a start offer is not observed projection.

The runtime suite disables LeakSanitizer for live libdbus fixtures because of
process-global caches; the separate init/destroy fixture enables it. Runtime
start/restart can block inside libdbus connection setup; only the active tick
has the zero-timeout, bounded-work contract. Neither a stub ACK nor a successful
helper response proves delivery, phone authentication, or projection.

## Gates that require target evidence

`cp_auth_broker` closes the offline session/helper completion gap. The new
`cp_spp_dbus` transport and `cp_runtime_broker` implement the caller-owned event
loop without product activation. Their scoped offline reviews pass. The broker
requires explicit caller-trusted identity, AP, consent/USB and receiver evidence;
mock evidence must not be relabeled as real attestation or working CarPlay.

The optional real-firmware SPP readback remains **BLOCKED** after its symlink
input-path guard failed; the owner explicitly chose to leave it blocked. No
alias resolution, retry through the direct build root, or bypass closes that
gate. Finding a usable vendor root for the separate package build does not
change this validation status.

Live OEM Bluetooth listener/RX/TX lifecycle and ABI, actual MFi chip calls,
trusted receiver identity/listener mapping, target loader/dependencies and
network-tool behavior, OEM handoff, and iPhone/USB coexistence remain unverified.
Physical deployment and parked-vehicle testing need separate explicit owner
confirmation. Offline development must not report these gates as passed.
